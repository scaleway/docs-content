Scaleway Object Storage runs on a shared, high-throughput distributed architecture that offers a strong price-performance ratio. It provides predictable throughput for core cloud workloads, such as log management, data lakes, automated backups, web asset delivery, and cloud-native distributed systems. This page describes the rate limits and quotas that apply to Object Storage, and how to scale your throughput within them.

## Performance baseline

Object Storage does not come with contractually guaranteed performance, such as dedicated input/output operations per second (IOPS) or fixed bandwidth. The throughput and latency you observe depend on the following factors:

- The sizing of your application and compute resources
- The number of concurrent requests
- The network path between your client and the storage endpoint

For more information on client-side tuning, see [Optimize your Object Storage performance](/object-storage/reference-content/optimize-object-storage-performance/).

### Performance by configuration

Latency and throughput are identical across the following configurations:

- Standard Multi-AZ storage class
- Standard One Zone storage class
- Public access (`s3.<REGION>.scw.cloud`) and private access (`s3-vpc.<REGION>.scw.eu`)

Objects stored using the Glacier storage class must be restored before use.

Object Lock has no impact on performance. Object Lock is an API-level governance and compliance mechanism (write once, read many, or WORM), and does not affect read speed, write speed, or retrieval time.

## Rate limits

Scaleway applies the same rate limits to all Object Storage endpoints, including S3 endpoints and bucket website endpoints. Each TCP/TLS connection supports up to:

- 3,000 requests per second for `GET` and `HEAD` operations
- 1,000 requests per second for all other operations, such as `PUT`, `DELETE`, and `LIST`

## Scale your throughput

Rate limits apply per connection, so you can scale your workload horizontally. Scaleway recommends the following practices:

- **Parallel connections**: Open multiple connections in parallel. The request volume you can send increases linearly with the number of connections.
- **Multipart uploads**: Split large objects into parts and upload them in parallel to increase the aggregate bandwidth. For more information, see [Multipart uploads](/object-storage/api-cli/multipart-uploads/).
- **Key prefix distribution**: Spread requests evenly across different object key prefixes. Avoid sequential or timestamp-based prefixes at the root of the bucket, as they send all traffic to a single partition. Distributed key names let Object Storage spread read and write operations across multiple internal shards.
- **Gradual ramp-up**: Increase your request volume progressively instead of sending sudden traffic spikes. A gradual increase lets Object Storage detect the load, split high-traffic key ranges, and allocate more resources.

With well-distributed key prefixes and a gradual ramp-up, a single bucket can handle tens of thousands of concurrent read and write requests per second.

## Quotas and limits

| Resource | Limit |
|---|---|
| Buckets per Project | 100 by default (up to 10,000) |
| Users | See [Organization quotas](/organizations-and-projects/organization/organization-quotas/) |
| Objects per bucket | No limit |
| Object size with `PutObject` | 5 GB |
| Object size with a multipart upload | 5 TB |
| Part size in a multipart upload | 5 MB – 5 GB (the last part can be smaller) |
| Parts per multipart upload | 1,000 |
| Lifecycle rules per bucket | No limit |
| Tags per bucket | 10 |
| Tags per object | 10 |
| Versions per object | 1,000,000 |

### Bucket quota

Scaleway applies the bucket quota per Project. The default value depends on the customer level of your Organization. Contact [Scaleway Support](https://console.scaleway.com/support/tickets/create) to request a higher quota.

Scaleway cannot raise the quota above 10,000 buckets per Project, as higher bucket counts increase the latency of the following operations:

- Object listing and metadata lookup
- Metering and billing processing

There is no limit on the total number of buckets per Organization. If you need more buckets, distribute them across multiple Projects in your Organization.
