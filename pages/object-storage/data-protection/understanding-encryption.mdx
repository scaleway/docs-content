Object Storage protects your data in transit with TLS, and at rest with server-side encryption. Server-side encryption encrypts each object when Object Storage writes it, and decrypts it when an authorized principal reads it. You can choose who manages the encryption keys: Scaleway, your Organization through Key Manager, or you. You can also encrypt your data yourself before you upload it.

## Encryption in transit

Object Storage endpoints accept HTTPS connections with `TLS 1.2` and `TLS 1.3`. Amazon S3-compatible tools use HTTPS by default when you configure an `https://` endpoint.

## Server-side encryption methods

| Method | Key management | Scope | Interfaces | Amazon S3 equivalent |
|---|---|---|---|---|
| [SSE-ONE](/object-storage/data-protection/sse-one/) | Scaleway creates, stores, and rotates the keys (AES-256) | Bucket default or each upload | Console, API, CLI | SSE-S3 |
| [SSE-KMS](/object-storage/data-protection/sse-kms/) | Your Organization manages a key encryption key (KEK) in [Key Manager](/key-manager/concepts/) (AES-256-GCM) | Bucket default or each upload | Console, API, CLI | SSE-KMS |
| [SSE-C](/object-storage/data-protection/sse-c/) | You provide the key with each request. Object Storage does not store it. | Each request | API, CLI | SSE-C |

### SSE-ONE

Server-side encryption with object native encryption (SSE-ONE) requires no key management. When you enable it on a bucket, Object Storage encrypts each new object with an individual key that Scaleway manages. Use SSE-ONE when you want encryption at rest without operational overhead.

### SSE-KMS

Server-side encryption with Key Management Service (SSE-KMS) uses a key encryption key (KEK) that you create and control in Key Manager. The KEK encrypts the data encryption keys (DEKs) that Object Storage uses for each object. You can rotate, disable, or protect the KEK in Key Manager.

SSE-KMS requires Key Manager permission sets for every principal that reads or writes encrypted objects, in addition to Object Storage permissions. Use SSE-KMS when your compliance requirements demand control over the keys.

### SSE-C

Server-side encryption with customer-provided keys (SSE-C) uses a 256-bit key that you send with each upload and download request. Object Storage uses the key to encrypt or decrypt the object, then deletes it, and only keeps a digest of the key to validate later requests. Use SSE-C when you must keep full custody of your keys, for example by storing them in [Secret Manager](/tutorials/object-storage-sse-c-with-secret-manager/).

<Message type="important">
With SSE-C, if you lose the encryption key of an object, you permanently lose access to the object. With SSE-KMS, deleting the KEK in Key Manager makes all objects encrypted with it permanently inaccessible.
</Message>

## How server-side encryption applies to objects

- Encryption happens when Object Storage writes an object. Enabling default encryption on a bucket does not encrypt the objects already stored in it. To encrypt an existing object, upload it again or copy it onto itself with encryption enabled.
- Disabling default encryption does not decrypt existing objects. Objects uploaded while encryption was enabled remain encrypted.
- A bucket has a single default encryption method, but you can specify another method for individual uploads.

## Client-side encryption

To make sure that Scaleway never has access to your unencrypted data or your keys, encrypt your data before you upload it. Client-side encryption is particularly suited to long-term archives stored in the [Glacier](/object-storage/storage-classes/understanding-storage-classes/#glacier) class.

You can use third-party tools such as [GPG](https://gnupg.org/), or tools that automate encrypted backups such as [Duplicity](https://wiki.debian.org/Duplicity) and [rclone crypt](https://rclone.org/crypt/). See the [Encrypting your Scaleway Object Storage data using Rclone](/tutorials/encrypt-s3-data-rclone/) tutorial.
