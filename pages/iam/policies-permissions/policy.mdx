IAM Policies are statements that define the permissions of users, groups, and applications in Scaleway Organizations.

They are composed of:

- a [principal](#principal) - a user, group, or application
- one or more IAM rules - consisting of [permission sets](#permission-sets) bound to a [scope](#scope)
- one or more IAM conditions - defined in Common Expression Language (CEL) expressions

## Principal

A principal is an entity that can be attached to a policy. Currently, you can attach either a [user](/iam/principals/users-groups-and-applications/#users), a [group](/iam/principals/users-groups-and-applications/#groups), or an [application](/iam/principals/users-groups-and-applications/#applications) to a policy. You can also select **AllUsers** or **AllApps** to attach the policy to every user or every application in your Organization at once. Only one principal can be attached to each policy.

<Message type="tip">
  If a user or application is the principal of multiple policies, whether as sole principal or as part of a group, all the permissions defined in each of these policies apply to that principal.
</Message>

## Rules

A rule is the part of a policy that defines the permissions of the [principal](/iam/concepts/glossary/#principal) attached to the policy, and the [scope](/iam/concepts/glossary/#scope) of these permissions. It consists of a scope (at Project level or Organization level) and one or more permission sets (e.g., "list all Instances").

<Lightbox image={image} alt="Example IAM policy showing a rule with scope and permission sets" />

<Message type="note">
  A policy can have one or many rules. Each rule is either an Allow rule (grants access) or a Deny rule (blocks access, acting as a security guardrail). The default starting point for any user or application other than the owner of the Organization is zero permissions. See [Allow and Deny rules](#allow-and-deny-rules) and [Permission resolution](#permission-resolution) for details.
</Message>

### Scope

A scope defines where the permission sets should apply. At Scaleway, a scope can be at Project or Organization level.

  - **Projects** group your Scaleway resources (e.g., Instances, Object Storage buckets, Managed Databases etc.) together. An Organization may have many Projects, or just one default Project. If you choose to define scope at the Project level, you can select one, many, or all Projects. When you then define the permission sets for this scope, you can give or deny access to different resources within the Project(s).
  - **Organizations** are made up of one or several Projects. IAM, billing, support and abuse tickets, and project management are managed at the Organization level, so choose an Organization scope to give or deny access to these features.

### Permission sets

A permission set consists of one or more permissions to perform actions on resources or features. Each permission set has a clear description, e.g., `InstancesFullAccess`, `InstancesReadOnly`, `RelationalDatabaseFullAccess`, `BillingReadOnly`.

You can find a detailed list of all permission sets available at Scaleway on the [permission sets reference page](/iam/policies-permissions/permission-sets/).

<Message type="important">
  Keep in mind that, due to replication and caching, any new configuration of permission sets may take up to 1 minute to apply.
</Message>

### Conditions

A condition is an additional layer of restrictions for your rule. You can scope the rule to specific user agents or IP addresses, and limit it to certain dates and times. Conditions are defined through [CEL](/iam/concepts/glossary/#common-expression-language-cel) expressions. In general, a condition expression consists of one or more statements that are joined by logical operators (`&&`, `||`, or `!`).

You can set up and configure conditions in the Scaleway console.

See [Understanding policy conditions](/iam/policies-permissions/understanding-policy-conditions/) to learn how they are set up and how you can define them.

### Allow and Deny rules

Each rule in a policy is either an Allow rule or a Deny rule.

Allow rules
: Grant the specified permission sets to the principal within the given scope. This is the standard way to give access.

Deny rules
: Guarantee that the specified permission sets can never be granted to the principal, regardless of any other Allow rules or policies. They act as security guardrails and are useful for enforcing governance policies (e.g., "no one can delete production Instances").

Deny rules take precedence over Allow rules. If a principal has both an Allow and a Deny rule covering the same permission set and scope, the Deny rule wins. See [Permission resolution](#permission-resolution) for the full evaluation order.

Deny rules use the same structure as Allow rules: a scope and one or more permission sets. They can also include [conditions](#conditions).

## Permission resolution

When a principal attempts an action, Scaleway evaluates access through a layered hierarchy. Each level can override the ones below it:.

## Example policy

The policy below states that the application `production-c` can create, list, delete and manage Instances and Databases in Project A, but for Object Storage it can only list and read the resources.

Principal
: IAM Application `production-c`

**Rule 1:**

Scope
: Project "A"

Permission set
: `InstancesFullAccess`, `ObjectStorageReadOnly`, `RelationalDatabasesFullAccess`

**Rule 2:**

Scope
: Project "F"

Permission set
: `ContainerRegistryFullAccess`, `ContainersReadOnly`, `RelationalDatabasesFullAccess`

<Message type="note">
  Allow policies do not compete with each other, they simply combine to grant all the permissions defined within them to any given principal. However, if a Deny rule covers the same permission set and scope, it takes precedence over any Allow rule. See [Permission resolution](#permission-resolution).
</Message>

**JSON policy example**

```json
{
  "application": "production-c",
  "rules": [
    {
      "projects": ["A"],
      "permission_sets": ["InstancesFullAccess", "ObjectStorageReadOnly", "RelationalDatabasesFullAccess"]
    },
    {
      "projects": ["F"],
      "permission_sets": ["ContainerRegistryFullAccess", "ContainersReadOnly", "RelationalDatabasesFullAccess"]
    }
  ]
}
```

You can add more rules to the policy to give `production-c` additional permissions in other Projects or at the Organization level.
