This page shows you how to configure [Grafana Alloy](https://grafana.com/docs/alloy/latest/) to push your **Instance metrics and logs** (the systemd journal and `/var/log` files) from a Scaleway Instance to Cockpit (Prometheus + Loki), and visualize them in a single dashboard.

It follows the same setup as the [Send metrics to Cockpit using Grafana Alloy](/cockpit/how-to/send-metrics-with-grafana-alloy/) article and extends it with logs collection and a curated dashboard.

<Requirements />

- A Scaleway account logged into the [console](https://console.scaleway.com)
- [Owner](/iam/concepts/glossary/#owner) status or [IAM permissions](/iam/concepts/glossary/#permission) allowing you to perform actions in the intended Organization
- [Created custom data sources of the **Metrics** type and the **Logs** type](/cockpit/how-to/create-external-data-sources/)
- Created an IAM application with an API key and assigned it an IAM policy with the `ObservabilityFullAccess` permission set. For detailed instructions, see [Create an API secret key](#create-an-api-secret-key).

<Message type="important">
 - Using default agent settings may collect unnecessary metrics, driving up resource consumption and your monthly bill. Find out [how to avoid additional costs when using Cockpit](/cockpit/reference-content/understanding-cockpit-usage/).
 - Sending metrics and logs for Scaleway resources or personal data using an external path is a billable feature. In addition, any data that you push yourself is billed, even if you send data from Scaleway products. See the [product pricing](https://www.scaleway.com/en/pricing/managed-services/#cockpit) for more information.
</Message>

## Create an API secret key

Your Grafana Alloy configuration must include an `X-Auth-Token` header with your Scaleway API secret key.

Follow these steps to create your API secret key:
1. [Create an IAM application](/iam/principals/create-application/).
2. [Create a policy](/iam/policies-permissions/create-policy/), making sure that:
    - When selecting the principal type, you choose the application you created in step 1. 
    - When adding rules, you select the **Resource management** > **Cockpit** > **ObservabilityFullAccess** permission set (it includes the `cockpit:metric:create` and `cockpit:log:create` permissions).
    - The scope of the policy includes the Project of your Cockpit, in the same region as your data sources.    
3. Go back to your IAM application, select the **API keys** tab, and click **Generate an API key**. 
4. In the **Generate an API keys** dialog box that appears:
    1. Provide an optional key description, and select a key expiration time. 
    2. Leave the Object Storage as **No, skip for now**. 
    3. Click **Generate API key**. A screen displays the access key and secret key for your new API key. Save the secret key in a secure place; it will not be shown again after closing the screen.

## Create your Instance and install Grafana Alloy

1. In the Scaleway console side menu, go to **Compute** > **CPU & GPU Instances**, and [create an Instance](/instances/how-to/create-an-instance/).
2. Open a terminal and execute the following command to connect to your Instance. You can retrieve the public IP address of your Instance from its **Overview** page > **Public Network** section.

            ```bash
            ssh root@<YOUR_INSTANCE_PUBLIC_IP>
            ```   
3. Install Grafana Alloy on the Instance. In this tutorial, we are using Grafana Alloy on an Ubuntu instance. See the [official Grafana documentation](https://grafana.com/docs/alloy/latest/set-up/install/) to find the commands to use depending on your operating system of choice.

## Configure Grafana Alloy to send metrics and logs to Cockpit

1. Create a folder named `config` on the Instance.
2. Inside the `config` folder, create a file named `cockpit.alloy`.
3. Paste the following configuration inside `cockpit.alloy`. Remember to replace:

   - `<METRICS_DATASOURCE_UUID>` with your Metrics data source UUID (You can retrieve it from the Scaleway console, from the **Monitoring** > **Cockpit** > **Data sources** tab.)
   - `<LOGS_DATASOURCE_UUID>` with your Logs data source UUID (you can retrieve it from the Scaleway console, from the **Monitoring** > **Cockpit** > **Data sources** tab).
   - `<REGION>` with your Cockpit region (e.g., fr-par)
   - `<API_SECRET_KEY>` with your IAM API key secret key

   ```bash
   // ---------------------------------------------------------------- METRICS
   
   prometheus.exporter.unix "node" {
     set_collectors = [
       "uname",
       "cpu",
       "cpufreq",
       "loadavg",
       "meminfo",
       "filesystem",
       "netdev",
       "stat",
     ]
   }
   
   prometheus.scrape "node" {
     scrape_interval = "10s"
     scrape_timeout  = "4s"
   
     targets    = prometheus.exporter.unix.node.targets
     forward_to = [prometheus.relabel.node.receiver]
   }
   
   prometheus.relabel "node" {
     // Constant labels so the dashboard job/instance variables match both
     // metrics and logs.
     rule {
       source_labels = []
       regex         = ""
       target_label  = "job"
       replacement   = "node"
       action        = "replace"
     }
     rule {
       source_labels = []
       regex         = ""
       target_label  = "instance"
       replacement   = "scw-instance"
       action        = "replace"
     }
   
     forward_to = [prometheus.remote_write.cockpit.receiver]
   }
   
   prometheus.remote_write "cockpit" {
     endpoint {
       url = "https://<METRICS_DATASOURCE_UUID>.metrics.cockpit.<REGION>.scw.cloud/api/v1/push"
       headers = {
         "X-Auth-Token" = "<API_SECRET_KEY>",
       }
     }
   }
   
   // ------------------------------------------------------------------- LOGS
   
   loki.write "cockpit" {
     endpoint {
       url = "https://<LOGS_DATASOURCE_UUID>.logs.cockpit.<REGION>.scw.cloud/loki/api/v1/push"
       headers = {
         "X-Auth-Token" = "<API_SECRET_KEY>",
       }
     }
   }
   
   // Systemd journal logs
   loki.source.journal "journal" {
     forward_to = [loki.relabel.add_dashboard_labels.receiver]
     labels     = { job = "journal" }
   }
   
   // Flat file logs (explicit paths, no glob)
   loki.source.file "varlogs" {
     targets = [
       {__path__ = "/var/log/syslog",   job = "syslog"},
       {__path__ = "/var/log/auth.log", job = "auth"},
       {__path__ = "/var/log/kern.log", job = "kern"},
       {__path__ = "/var/log/dpkg.log", job = "dpkg"},
       {__path__ = "/var/log/dmesg",    job = "dmesg"},
     ]
     forward_to = [loki.relabel.add_dashboard_labels.receiver]
   }
   
   // Normalize labels for the curated dashboard: it expects container_name,
   // service_name and instance. container_name is set to "host" for Instance
   // logs so the container_name="host" matcher of the dashboard selects them.
   loki.relabel "add_dashboard_labels" {
     rule {
       source_labels = ["__meta_docker_container_name"]
       regex         = "(.*)"
       target_label  = "container_name"
       action        = "replace"
     }
     rule {
       source_labels = ["__meta_docker_container_name"]
       regex         = ""
       target_label  = "container_name"
       replacement   = "host"
       action        = "replace"
     }
   
     // service_name: fall back to the job label so each source becomes its own row.
     rule {
       source_labels = ["job"]
       regex         = "(.*)"
       target_label  = "service_name"
       action        = "replace"
     }
   
     // instance: constant hostname so the dashboard instance variable/donut works.
     rule {
       source_labels = []
       regex         = ""
       target_label  = "instance"
       replacement   = "scw-instance"
       action        = "replace"
     }
   
     forward_to = [loki.write.cockpit.receiver]
   }
   ```

4. Change directory to quit the `config` folder and start Grafana Alloy:

   ```bash
   alloy
   ```

5. Run the configuration:

   <Message type="note">
   Reading the systemd journal (`loki.source.journal`) requires root access or membership in the `systemd-journal` group. Run Alloy with `sudo` if needed.
   </Message>

   ```bash
   alloy run config/cockpit.alloy
   ```

   You should see Alloy load the configuration and start pushing metrics and logs data. If you get a `403`, your API key is missing the **ObservabilityFullAccess** (`cockpit:metric:create`, `cockpit:log:create`) permission set, or is not in the same region or Project as your data sources.


## Visualize your metrics and logs

1. In the [console](https://console.scaleway.com/) side menu, click **Monitoring** > **Cockpit**. The **Cockpit** overview page opens.
2. Click **Access Grafana** to open your preconfigured dashboards in Grafana. You are redirected to the Grafana website.
3. Log in to your Grafana account. The Grafana overview page opens.
4. Click **Dashboards**, then click the **New** side menu. A dropdown appears.
5. Click **Import** to import a dashboard.
6. Copy the dashboard JSON from the [Appendix: Dashboard specification](#appendix-dashboard-specification), paste it into the **Import via dashboard JSON model** field, and click **Load**.

   The JSON code block specifies a dashboard called **Cockpit Instance - Host Metrics & Logs** (uid `cockpit-instance-metrics-logs`). 
7. The following fields appear in the import form. Ensure that you select both data sources explicitly(**DS_PROMETHEUS** and **DS_LOKI**).
   - **Name** — This is pre-filled with the name **Cockpit Instance - Host Metrics & Logs**.
   - **Folder** — Use the dropdown to select a folder in which to store your dashboard. 
   - **DS_PROMETHEUS** — Use the dropdown to select your custom Cockpit metrics (Prometheus) data source.
   - **DS_LOKI** — Use the dropdown to select your custom Cockpit logs (Loki) data source.

   <Lightbox image={image} alt="A screenshot showing the Import dashboard form in Grafana with the Name, Folder, DS_PROMETHEUS, and DS_LOKI fields." />
8. Click **Import**. 

   The dashboard opens with the **Host** panel showing Instance metrics (uptime, CPU, memory, network) and the **Logs** panel showing logs (log volume and live logs). 
   
   If your data sources were created less than 24 hours ago, click the clock icon and adjust the time range to match its creation time.
   
   The dashboard expects the `container_name`, `service_name`, and `instance` labels, which `config/cockpit.alloy` sets via its relabel stages (`container_name` is set to `host` for Instance logs). 

   <Lightbox image={image2} alt="A screenshot showing the Instance dashboard with metrics displayed for uptime, CPU, memory, network." />

   <Lightbox image={image3} alt="A screenshot showing the Instance dashboard with log volume and live logs data." />

9. You can also explore your metrics and logs directly in Grafana **Explore**. 

   Use **Label filters** to narrow down your queries (e.g., `instance = scw-instance` for metrics and `service_name = auth` or `syslog` or `auth` for logs).

## (Optional) See your metrics and logs in action with a stress test

The pipeline runs continuously: while Alloy is up, metrics and logs are scraped from your Instance, pushed to Cockpit, and shown in the dashboard. To see this live, run a short memory stress test with `stress-ng` (not installed by default) and watch the dashboard react within a few scrape intervals.

1. Connect to your Instance and install `stress-ng`:

   ```bash
   ssh root@<YOUR_INSTANCE_PUBLIC_IP>
   apt-get update && apt-get install -y stress-ng
   ```

2. Start a background stress that holds about 50% of your Instance RAM for 5 minutes, and log a few lines through the systemd journal (so you can see logs flowing too):

   ```bash
   total_kb=$(awk '/MemTotal/{print $2}' /proc/meminfo)
   logger "Starting memory stress test: ${total_kb} KB total, allocating ~50% for 5 min"
   nohup stress-ng --vm 1 --vm-bytes $((total_kb / 2))K --vm-keep -t 300 >/tmp/stress-ng.log 2>&1 &
   ```

3. In Grafana, open your dashboard and extend the time range to the last 5 minutes. Within 1 or 2 scrape intervals (10s each), you should see the following:
   - the **Memory usage** panel climbs to ~50%
   - the **Log volume** panel counts new `journal` entries (from `logger`), and the **Live logs** panel shows them in real time
   - the **Uptime**, **CPU usage**, and **Network traffic** panels keep updating every 10 seconds, proving that metrics keep flowing

4. When you are done, stop the test and log it:

   ```bash
   pkill stress-ng
   logger "Memory stress test stopped"
   ```

   The `stress-ng` output is saved to `/tmp/stress-ng.log` (`successful run completed in 300s` when it ends).
