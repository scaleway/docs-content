This page explains how to reuse components in Data Orchestrator workflow definitions.
For information on other tasks and concepts, see the [Data Orchestrator DSL Reference](/data-orchestrator/reference-content/dsl-reference/).

In the following examples, replace the placeholders with the appropriate values.

## Use environment variables

The following environment variables are injected by default in the workflow runs to improve and optimize data management.

|      Variable name       |                  Description                   |              Sample value              |
| :----------------------- | :--------------------------------------------- | :------------------------------------- |
| `region`                 | Region of the workflow run                     | `fr-par`                               |
| `organizationId`         | ID of the Organization of the workflow         | `00000000-0000-0000-0000-000000000000` |
| `projectId`              | ID of the Project of the workflow              | `00000000-0000-0000-0000-000000000000` |
| `workflowDefinitionId`   | ID of the workflow definition                  | `00000000-0000-0000-0000-000000000000` |
| `workflowDefinitionName` | Name of the workflow definition                | `"dor-workflow-name"`                  |
| `workflowVersionId`      | ID of the workflow version                     | `00000000-0000-0000-0000-000000000000` |
| `workflowRunId`          | ID of the workflow run                         | `00000000-0000-0000-0000-000000000000` |
| `triggerType`            | Type of trigger that launched the workflow run | `manual` or `scheduled`                |

To reuse these environment variables, use the syntax `${ $workflow.<ENVIRONMENT_VARIABLE> }`. For example: 

```yaml
do:
  - <TASK_NAME>:
      if: ${ $workflow.workflowDefinitionName == "<WORKFLOW_NAME_001>" }
      call: serverless_job
      with:
        id: "<SERVERLESS_JOB_ID>"
        region: "<REGION>"
```

When a workflow executes a Serverless Job, the environment variables are injected into the job with the following format:

- `SCW_WOFL_REGION`
- `SCW_WOFL_ORGANIZATION_ID`
- `SCW_WOFL_PROJECT_ID`
- `SCW_WOFL_DEFINITION_ID`
- `SCW_WOFL_DEFINITION_NAME`
- `SCW_WOFL_VERSION_ID`
- `SCW_WOFL_RUN_ID`
- `SCW_WOFL_TRIGGER_TYPE`

<Message type="tip">
  To make it shorter, set a variable in your workflow definition using [set](/data-orchestrator/reference-content/dsl-reference#set).
</Message>

## Use secrets from Secret Manager

Data Orchestrator can also use secrets stored in Scaleway [Secret Manager](https://www.scaleway.com/en/secret-manager/).
To reuse secrets in your workflow definition, use `secrets` to reference them.

The following example shows how to reference and use a secret for a basic authentication in a workflow definition:

```yaml
use:
  secrets:
    - <BASIC_SECRET_NAME>
  authentications:
    <AUTHENTICATION_VARIABLE_NAME>:
      basic:
        use: <BASIC_SECRET_NAME>
do:
  - <TASK_NAME>:
      call: http
      with:
        method: GET
        endpoint:
          uri: <URI_EXAMPLE>
          authentication:
            use: <AUTHENTICATION_VARIABLE_NAME>
```

<Message type="note">
  The values of the secret must match the expected format for the authentication type. For example, for basic authentication, the secret must contain a `username` and a `password`. For more information, see [Authentication](/data-orchestrator/reference-content/dsl-reference#authentication).
</Message>

In addition, it is also possible to use secrets directly in a jq expression, for example with `${ $secrets.'<BASIC_SECRET_NAME>'.username }` or `${ $secrets.'<BASIC_SECRET_NAME>'.password }`.
