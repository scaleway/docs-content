Data Orchestrator in Code view requires that you upload a YAML file to use as a workflow definition.
This page lists the action tasks specifically developed for Data Orchestrator workflow definitions.
For information on other tasks and concepts, see the [Data Orchestrator DSL Reference](/data-orchestrator/reference-content/dsl-reference/).

In the following examples, replace the placeholders with the appropriate values. The `namespace` and `name` fields are required, and can be used as metadata to help organize YAML files.

## Action tasks
<Tabs>
  <TabsTab label="Serverless Job">
    The Scaleway Serverless Job Call lets you run recurring and autonomous tasks in the cloud.

    The following example shows a workflow that calls a Serverless Job. Copy Serverless Job IDs from the [Serverless Jobs page](https://console.scaleway.com/serverless-jobs/) of the console.

    <Message type="important">
      The workflow and the Serverless Job must be in the same project.
    </Message>

      ```yaml
      document:
        dsl: 1.0.3
        namespace: <NAMESPACE_NAME>
        name: <WORKFLOW_NAME>
        version: 1.0.0
      do:
        - callServerlessJob:
            call: "serverless_job"
            metadata:
              description: "The first job"
            with:
              id: "<SERVERLESS_JOB_ID>"
              region: "<REGION>"
      ```
  </TabsTab>

  <TabsTab label="Serverless Function">
    The Serverless Function Call lets you call the default endpoint of a Serverless Function.
   
    Instead of using an HTTP endpoint (with potential authentication), you provide the function identifier (`id`) and the region (`region`) to invoke the function. The call handles authentication automatically.
    
    The following example shows how to call a Serverless Function. Copy Serverless Function IDs from the [Serverless Functions page](https://console.scaleway.com/functions/) of the console.

    <Message type="important">
      The workflow and the Serverless Function must be in the same project.
    </Message>

      ```yaml
      document:
        dsl: 1.0.3
        namespace: <NAMESPACE_NAME>
        name: <WORKFLOW_NAME>
        version: 1.0.0
      do:
        - callServerlessFunction:
            call: "serverless_function"
            with:
              method: GET
              id: "<SERVERLESS_FUNCTION_ID>"
              region: "<REGION>"
              output: "response"    
      ```
  </TabsTab>
  
  <TabsTab label="Serverless Container">
    The Serverless Container Call lets you call the default endpoint of a Serverless Container.
   
    Instead of using an HTTP endpoint (with potential authentication), you provide the container identifier (`containerId`) - or the container name (`name`) together with the namespace identifier (`namespaceName` or `namespaceId`) - and region (`region`) to invoke the container. The call handles authentication automatically.
    
    The following example shows how to call a Serverless Container. Copy Serverless Container IDs from the [Serverless Containers page](https://console.scaleway.com/containers/) of the console.
    <Message type="important">
      The workflow and the Serverless Container must be in the same project.
    </Message>

      ```yaml
      document:
        dsl: 1.0.3
        namespace: <NAMESPACE_NAME>
        name: <WORKFLOW_NAME>
        version: 1.0.0
      do:
        - callServerlessContainer:
            call: "serverless_container"
            with:
              method: GET
              id: "<SERVERLESS_CONTAINER_ID>"
              region: "<REGION>"
              output: "response"
      ```
  </TabsTab>

  <TabsTab label="HTTP Call">
    The HTTP Call lets you call any external service over HTTP.
    The following example shows how to make an HTTP call.

      ```yaml
      document:
        dsl: 1.0.3
        namespace: <NAMESPACE_NAME>
        name: <WORKFLOW_NAME>
        version: 1.0.0
      do:
        - httpCall:
            call: "http"
            with:
              method: GET
              url: "<url>"
              output: "response"
      ```
  </TabsTab>

  <TabsTab label="Set">
    The set tasks lets you set data to be reused in the workflow.
    The following example shows how to set a shape and a color.

      ```yaml
      document:
        dsl: '1.0.3'
        namespace: <NAMESPACE_NAME>
        name: <WORKFLOW_NAME>
        version: '1.0.0'
      do:
        - setShape:
            set:
              shape: circle
              size: ${ .configuration.size }
              fill: ${ .configuration.fill }
        - setColor:
            set: ${ .configuration.color }
      ```
  </TabsTab>

  <TabsTab label="Raise">
    The raise task lets your workflow generate error conditions, and implement error handling and fault management strategies.
    
    The following example shows how to handle tickets according to their priority.

      ```yaml
      document:
        dsl: '1.0.3'
        namespace: <NAMESPACE_NAME>
        name: <WORKFLOW_NAME>
        version: '1.0.0'
      do:
        - processTicket:
            switch:
              - highPriority:
                  when: .ticket.priority == "high"
                  then: escalateToManager
              - mediumPriority:
                  when: .ticket.priority == "medium"
                  then: assignToSpecialist
              - lowPriority:
                  when: .ticket.priority == "low"
                  then: resolveTicket
              - default:
                  then: raiseUndefinedPriorityError
        - raiseUndefinedPriorityError:
            raise:
              error:
                type: https://fake.com/errors/tickets/undefined-priority
                status: 400
                instance: /raiseUndefinedPriorityError
                title: Undefined Priority
        - escalateToManager:
            call: http
            with:
              method: post
              endpoint: https://fake-ticketing-system.com/tickets/escalate
              body:
                ticketId: ${ .ticket.id }
        - assignToSpecialist:
            call: http
            with:
              method: post
              endpoint: https://fake-ticketing-system.com/tickets/assign
              body:
                ticketId: ${ .ticket.id }
        - resolveTicket:
            call: http
            with:
              method: post
              endpoint: https://fake-ticketing-system.com/tickets/resolve
              body:
                ticketId: ${ .ticket.id }
      ```
  </TabsTab>

  <TabsTab label="Wait">
    The wait task lets your workflow pause or delay their execution for a specified period of time.
    
    The following example shows a task that waits 90 seconds before continuing the workflow.

      ```yaml
      document:
        dsl: '1.0.3'
        namespace: <NAMESPACE_NAME>
        name: <WORKFLOW_NAME>
        version: '1.0.0'
      do:
        - waitAWhile:
            wait:
              minutes: 1
              seconds: 30
      ```
  </TabsTab>
</Tabs>
