Managed Database for PostgreSQL and MySQL lets you manage the permissions of your database users from the Scaleway console, API, and CLI. The user permissions API covers most use cases, but has some limitations.

This page explains why a user permission can switch to **Custom**, and how to choose between managed and non-managed logical databases depending on the Structured Query Language (SQL) commands you need.

<Requirements />

- A Scaleway account logged in to the [console](https://console.scaleway.com)
- [Owner](/iam/concepts/glossary/#owner) status or [IAM permissions](/iam/concepts/glossary/#permission) allowing you to perform actions in the intended Organization
- A [PostgreSQL or MySQL Database Instance](/managed-databases-for-postgresql-and-mysql/how-to/create-a-database/)

## Custom permissions

When you create a user or update their permissions, you choose one of the following permission types for each logical database:

- **None:** No access to the database
- **Read:** Allow users to read tables and fields in a database
- **Read/Write:** Allow users to read/write content in databases
- **All:** Allow users to create schemas and tables in addition to Read/Write rights

After you set the permissions, the database can change. For example, someone creates new tables or installs an extension. For security purposes, Scaleway does not apply the user permissions for that database to new objects. The user permission for that database switches to **Custom** - the user keeps the rights they had when you last updated their permissions, but has no rights on the new objects.

The permission also switches to **Custom** when you make it more granular per object. For example, you give a user the **Read** permission on a database, then grant them read/write rights on a single table of that database.

<Message type="tip">
  To apply the permissions of a user to the whole database again, including new objects, update the permissions of the user. You can update the permissions of a user at any time. For more information, see [Set permissions for an existing user](/managed-databases-for-postgresql-and-mysql/how-to/manage-users/#set-permissions-for-an-existing-user).
</Message>

## Managed and non-managed logical databases

You can create a logical database in the following ways:

- From the Scaleway console, API, or CLI
- By running an SQL query directly on your Database Instance

Each option has advantages and drawbacks:

| | Managed logical database | Non-managed logical database |
|---|---|---|
| Creation method | Scaleway console, API, or CLI | SQL query on the Database Instance |
| User permissions API | Supported. See [Set permissions for an existing user](/managed-databases-for-postgresql-and-mysql/how-to/manage-users/#set-permissions-for-an-existing-user). | Not supported. You manage permissions manually with SQL queries. |
| `GRANT CONNECT` and `BYPASSRLS` commands | Not allowed | Allowed |

On managed logical databases, you can get a result similar to `GRANT CONNECT` by giving the user the **Read** permission, then revoking the rights you do not need with a `REVOKE` statement.

`BYPASSRLS` is available on PostgreSQL only and lets a role bypass row-level security policies. For more information, see the [PostgreSQL documentation about row security policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

## Permissions for many databases and users

If your Database Instance has a large number of databases and users, the Scaleway console may have difficulty applying permission changes. For these use cases, use the [Scaleway API](https://www.scaleway.com/en/developers/api/managed-databases-for-postgresql-and-mysql/), the [Scaleway CLI](https://github.com/scaleway/scaleway-cli), or [Terraform](https://registry.terraform.io/providers/scaleway/scaleway/latest/docs) instead.
