This page lists the different features and limitations of Scaleway File Storage.

## Features

### Shared file systems

File Storage allows you to keep data in an organized hierarchy of files and folders that multiple Instances can access at the same time. Each file system can be attached to several Instances, and each Instance can have several file systems attached to it.

### Performance scaling with capacity

IOPS and throughput scale linearly with the provisioned capacity of your file system, up to 25,000 IOPS and 200 MB/s at 2 TB. Refer to the [performance scaling documentation](/file-storage/reference-content/performance-scaling/) for more information.

### Resizing

You can increase or decrease the size of a file system from the Scaleway console. Refer to the [dedicated documentation](/file-storage/how-to/resize-file-system/) for more information.

### Snapshots

You can create point-in-time snapshots of your file systems. Refer to the [dedicated documentation](/file-storage/api-cli/manage-snapshots-api/) for information on how to manage snapshots using the Scaleway API.

### Kubernetes Kapsule integration

The Scaleway File Storage Container Storage Interface (CSI) driver allows you to use file systems in Kubernetes Kapsule and Kosmos clusters. The CSI driver supports dynamic provisioning, import of existing file systems, volume upsizing, and the `ReadWriteOnce`, `ReadOnlyMany`, and `ReadWriteMany` access modes. Refer to the [dedicated documentation](/kubernetes/how-to/use-sfs-with-kubernetes/) for more information.

### Data protection and resilience

Scaleway automatically encrypts all data at rest on physical disks, and routes all transfers over a dedicated, isolated network.

Scaleway distributes your data across multiple independent storage nodes and disks within one Availability Zone (triple replication). This architecture prevents data loss from individual hardware failures.

## Limitations

### Same-region requirement

You can only attach a file system to Instances located in the same [region](/file-storage/concepts/#region) as the file system.

### File system attachments per Instance

The maximum number of file systems you can attach to an Instance depends on the Instance type. Refer to the [File Storage and Instances selection guidelines](/file-storage/reference-content/file-system-instance-selection/#file-system-attachments-per-compatible-instance-type) for the full list of limits per Instance type.

### File system size

- The size of a file system must be between 25 GB and 50 TB.
- You can only resize a file system by increments of 1 GB.
- You cannot reduce the size of a file system below its currently used space.

### Performance cap

IOPS and throughput reach their maximum values at 2 TB of provisioned capacity. Provisioning beyond 2 TB increases the available storage, but does not further increase performance.

The performance of a file system also depends on the number of attached Instances, the attached Instance types, and the workload. Refer to the [File Storage and Instances selection guidelines](/file-storage/reference-content/file-system-instance-selection/) for more information.

### File locking

Scaleway File Storage only supports advisory locking, and does not support the `flock` syscall. Read/write operations do not check for conflicting locks before executing.

Therefore, File Storage is not suited for applications that rely on `flock` to manage concurrent access to files.

Scaleway recommends using File Storage for the following use cases:

- Content Management Systems (CMS) with no strict file locking requirements
- AI and machine learning workloads, to share model weights and datasets across a cluster of GPU or CPU Instances
