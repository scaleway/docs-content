## Problem

After renaming a Kubernetes cluster via the Scaleway console, you observe the following issues:

- Pods stuck in `ContainerCreating` state
- Slow restart of CSI driver pods
- Internal DNS resolution failures
- ConfigMap mounting errors with messages such as:
  ```
  MountVolume.SetUp failed for volume "kube-api-access-xxxxx": failed to sync configmap cache
  ```
- CSI driver unmount errors:
  ```
  umount: can't unmount /tmp/kubelet-detect-safe-umount...: Invalid argument
  ```
- API server conflict errors:
  ```
  the object has been modified; please apply your changes to the latest version and try again
  ```
- Degradation of cluster response time
- Scheduled jobs failing to start

## Cause

Renaming a Kubernetes cluster is not a cosmetic change. The cluster name is used in several control-plane components, including the autoscaler configuration. When you rename a cluster, it triggers:

1. A complete redeployment of the control plane
2. A redeployment of the job that injects managed resources into your cluster
3. Automatic restart of all CSI driver pods (which may update to new versions if a release was recently published)

During this redeployment period, control-plane components (Cloud Controller Manager, autoscaler, CSI drivers, etc.) cannot function normally while waiting for the API server pods to become ready. This results in temporary disruption to your workloads.

## Possible solutions

### Wait for the control plane to stabilize

In most cases, the cluster returns to normal operation within 1 to 2 hours after the rename. The control-plane components will automatically recover once the API server pods are ready and the managed resources are reinjected.

**Recommended actions:**

1. Monitor the cluster status via the Scaleway console.
2. Check the status of control-plane components:
   ```bash
   kubectl get pods -n kube-system
   ```
3. Wait for all pods to reach the `Running` state.
4. Verify that scheduled jobs start executing normally.
5. Test internal DNS resolution from within a pod.

### Replace affected nodes (if issues persist)

If pods remain stuck in `ContainerCreating` state after more than 2 hours, the nodes hosting those pods may need to be replaced:

1. Identify the affected nodes:
   ```bash
   kubectl get pods --all-namespaces -o wide | grep ContainerCreating
   ```
2. Drain the affected node (optional, if workloads can be rescheduled):
   ```bash
   kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data
   ```
3. Replace the node via the Scaleway console or by recycling the node pool.
4. Verify that new pods schedule correctly on the replacement nodes.

### Prevent future issues

To avoid disruption resulting from cluster renaming:

- Avoid renaming production clusters during peak usage periods.
- Schedule renames during maintenance windows when workload impact is acceptable.
- Communicate with your team before performing a rename operation.
- Monitor cluster health closely for 1-2 hours after any rename.
